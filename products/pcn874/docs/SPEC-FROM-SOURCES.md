# PCN874 record layout, rendered from open-source implementations

**What this file is.** The Israeli VAT detailed report (`דוח מע"מ מפורט`, PCN874) is a fixed-width
ASCII text file uploaded to the Israel Tax Authority. The official layout is published by the ITA
as a PDF. **We could not open that PDF** — every URL for it is egress-blocked from the container
this was written in (verified, see §6). So every field below is rendered from **open-source code
that writes or reads the format**, and every row carries the repo, path and line that supports it.

**What this file is not.** It is not the official specification and it is not a legal statement.
Where the implementations disagree, §5 records the disagreement instead of quietly choosing.
Under `MISSION.md` rule 4 no legal figure or format rule ships that was not rendered from a
source; the sources here are code, not the ITA document, and that limit is stated on every
outward-facing page of this product.

Written 2026-09-07.

### 1.1 Are they independent?

Yes, for the three used. Different authors, different languages, different decades, no shared code:

- `accounter` is Gil Gardosh's TypeScript package (`@accounter/pcn874-generator`, v0.6.7 at time of
  reading). Its README cites the ITA's own English 874 PDF as its basis.
- `linet3` is the Israeli open-source accounting suite "Linet 3.0" by Adam Ben Hur, PHP on Yii2.
  It carries the layout as an English comment block written independently of anything above.
- `rcbuilder` is a standalone C# builder written for the 2023 reporting period, with its own
  field-width comments **and committed output files** — which makes it the only source here that
  offers an *artefact* to measure rather than a claim to read.

Repos that are **not** independent of `accounter` and were not counted: `gilgardosh/accounter-toolkit`
(same author, the earlier monorepo — this is the `@accounter-toolkit/pcn874-generator@0.4.1` the
colony sweep audited), `willfranck/Accounter` (fork), `asafo/Linet` (the earlier Linet lineage,
same project family as `linet3`).

### 1.2 One source found and deliberately excluded

`amitpo23/cfo` (`src/cfo/services/pcn874.py`) writes a PCN874-shaped file, but its own module
docstring disqualifies it as corroboration (lines 9–13):

> IMPORTANT — DRAFT STRUCTURE: the record types (O/S1/L/X) and field order follow the published
> מבנה-אחיד, but **exact byte offsets evolve by spec version**. Output is marked a draft to validate
> against the current official spec before submission; it is **NOT a guaranteed-conformant file**.

and again at lines 39–42, on the sign representation: *"PLACEHOLDER לאימות … הייצוג המדויק
(מיקום/תו הסימן) טעון אימות מול המפרט הרשמי"*. A source that says its own offsets are unverified
cannot be used to verify anyone else's. Its layout does in fact differ from all three used sources
(2-character record codes `S1`/`L` written into the file, no `refGroup`, no reserved trailing field,
`X` + record-count trailer instead of `X` + dealer id, CRLF). It is listed here so a later session
does not "discover" it and treat the disagreement as unexplained.

### 1.3 Licence consequences for this product

- `accounter` is MIT: code and text may be reused with attribution. We reuse **neither** — only facts.
- `linet3` is AGPL-3.0 and `rcbuilder` has **no licence at all**. Field offsets and widths are facts
  about a government file format, not expression, so citing them is fine; **copying their code or
  their sample files is not.** Every fixture in `tests/fixtures/` is therefore generated by
  `scripts/make-fixtures.mjs` from the table below, with invented digits. Nothing was copied from
  any source repo.

### 4.1 Record-type letters

The field in the file is **one character**. All three sources agree on that (`accounter` writes
`entryType.valueOf()[0]`, schemas.ts:158; `rcbuilder`'s enum members are single letters,
PCN874Manager.cs:281-293; `linet3` writes `%1s`, Docs.php:206). The eleven letters:

| letter | `accounter` name (types.ts) | Hebrew | side |
|---|---|---|---|
| `S` | `SALE_REGULAR` (`S1`) / `SALE_ZERO_OR_EXEMPT` (`S2`) | עסקה רגילה מזוהה / עסקה אפס מזוהה | sale |
| `L` | `SALE_UNIDENTIFIED_CUSTOMER` (`L1`) / `SALE_UNIDENTIFIED_ZERO_OR_EXEMPT` (`L2`) | עסקה רגילה לא מזוהה / עסקה אפס לא מזוהה | sale |
| `M` | `SALE_SELF_INVOICE` | חשבונית עצמית (עסקה) | sale |
| `Y` | `SALE_EXPORT` | ייצוא | sale |
| `I` | `SALE_PALESTINIAN_CUSTOMER` | לקוח רש"פ | sale |
| `T` | `INPUT_REGULAR` | תשומה רגילה | input |
| `K` | `INPUT_PETTY_CASH` | קופה קטנה | input |
| `R` | `INPUT_IMPORT` | רשימון יבוא | input |
| `P` | `INPUT_PALESTINIAN_SUPPLIER` | ספק רש"פ | input |
| `H` | `INPUT_SINGLE_DOC_BY_LAW` | מסמך אחר | input |
| `C` | `INPUT_SELF_INVOICE` | חשבונית עצמית (תשומה) | input |

Sources: `accounter` types.ts:4-86 (all eleven, with the two-character logical codes) and index.ts:65
(the allow-list `['C','H','I','K','L','M','P','R','S','T','Y']`); `rcbuilder` PCN874Manager.cs:281-293
(the same eleven letters as an enum); `linet3` Docs.php:192-196 (uses only `S` and `T`).

**Open question, not resolved here:** `accounter` keeps two-character codes `S1/S2/L1/L2` in its own
API and GraphQL enum (`packages/client/src/helpers/pcn874.ts:3-17`) but writes only the first
character to the file, so **a file written by any of these three cannot distinguish a taxable sale
from a zero-rated one by its record type**. Either the distinction is carried elsewhere (a zero
`totalVat`, most plausibly) or the file field is really two characters and every source here is
wrong — but a two-character field would make the detail record 61 characters, and the measured
artefact is 60. Recorded as §5.5; must be settled against the ITA PDF.

## 5. Where the sources disagree

Recorded, not silently resolved. Each row says what this validator does and why.

### 5.1 Width of the last header field (`reportedVat`, סכום מדווח) — 11 digits or 9?

| source | claim |
|---|---|
| `accounter` | sign + **11** digits (`numToSignedString(value, 11)`, schemas.ts:44), header total 131, asserted by its own validator at index.ts:40 |
| `rcbuilder` | sign + **11** digits (PCN874Manager.cs:401 comment "11 digits", :472 `PadLeft(11,'0')`) |
| `rcbuilder` artefact | line 1 of `PCN874_Sample.txt` measures **131** characters, and the final `-` sits at offset 119 followed by 11 digits |
| `linet3` | its layout comment says `A1` + `N9` for "total to pay" (FormReportPcn874.php:69-70), which would make the header **129** |

`linet3` is also internally inconsistent here: its `sprintf` format string (FormReportPcn874.php:90)
has **20 conversion specifications for 21 arguments**, so from `i_doc_count` onward every value lands
in the wrong specifier and its emitted header matches neither 131 nor its own comment.

**What this validator does:** requires 131, and says so in the finding text along with the
`linet3` minority reading. Two independent sources plus a measured artefact against one source that
does not agree with itself.

### 5.2 The last 9 characters of a detail record

| source | claim |
|---|---|
| `accounter` v0.6.7 (2025+) | `allocationNumber` — "Short allocation number – last 9 digits of full number", מספר הקצאה קצר (schemas.ts:318-327) |
| `rcbuilder` (2023) | `FutureData`, "9 digits (all zero)" (PCN874Manager.cs:313) |
| `linet3` (2014-2015) | literal `000000000` (Docs.php:187,206) |

All three agree the field is 9 digits at offset 51. They disagree about what goes in it, and the
disagreement is explained by date: Israel's allocation-number (מספר הקצאה) regime post-dates the C#
and PHP code. Note this is also the field that makes the colony sweep's audit of
`@accounter-toolkit/pcn874-generator@0.4.1` (Feb 2024) stale — that version had no such field.

**What this validator does:** requires 9 digits; accepts all-zeros and any other 9 digits equally.
Whether a non-zero allocation number is *required* for a given invoice is a legal question this
product does not answer.

### 5.3 `zeroOrExemptSalesAmount` — an amount, despite `accounter`'s field name

`accounter` calls it `zeroValOrExemptSalesCount` and types it `.int()` (schemas.ts:33-36), which
reads like a record count. Its own doc comment on the same field says *"Total of zero value/exempt
sales for period / עסקאות פטורות / אפס"* (schemas.ts:122-126) — an amount. `linet3` calls it
`t_exclude_vat`, "total exclude vat", and accumulates document subtotals into it
(FormReportPcn874.php:62-63,133). `rcbuilder` sums `TotalInvoiceAmount` into it
(PCN874Manager.cs:489-493). Two sources and one of `accounter`'s own comments say **amount**; only
`accounter`'s identifier says count.

**What this validator does:** treats it as an amount and names it `zeroOrExemptSalesAmount`. No rule
depends on the distinction, so nothing breaks if the PDF says otherwise — but a future generator
would get this wrong by copying the `accounter` name.

### 5.4 Which detail records feed `inputsCount` and `equipmentInputsVat`

| source | claim |
|---|---|
| `accounter` | `inputsCount` is "Total number of records for inputs (other and equipment)" (schemas.ts:137-141); `equipmentInputsVat` is a real input (schemas.ts:132-136) |
| `rcbuilder` | `inputsCount` counts **only `T` records** (PCN874Manager.cs:399,477-480); `equipmentInputsVat` is hardcoded to zeros with the note "תשומות ציוד - 0 קבוע" (PCN874Manager.cs:398, and the header notes at :36) |
| `linet3` | counts its own document types 13 and 14 — the split is by its internal doctype, not by PCN874 letter (FormReportPcn874.php:142-148) |

So it is **unsettled whether `K`, `R`, `P`, `H`, `C` records count toward `inputsCount`.**

**What this validator does:** cross-checks `inputsCount` against all input-letter records as a
**warning** carrying this disagreement, never an error. `salesRecordCount` is checked the same way
(warning) — there the sources agree in substance (all sales records, taxable and zero/exempt
together: `accounter` schemas.ts:116-121, `rcbuilder` :496-500) but `M`/`Y`/`I` are unexercised by
`rcbuilder`, which only ever emits `S`, `L` and `T`.

### 5.5 Footer letter: `X` or `Z`?

| source | claim |
|---|---|
| `accounter` | `X` + 9-digit dealer id, 10 characters (`footerBuilder`, builders.ts:40-42; asserted at index.ts:51-57) |
| `rcbuilder` | `X` + 9-digit dealer id (PCN874Manager.cs:531 and :569) |
| `rcbuilder` artefact | last line of both committed samples is `X` + 9 digits, 10 characters |
| `linet3` | **`Z`** + 9-digit dealer id (FormReportPcn874.php:94-99) |
| `cfo` (excluded) | `X` + 9-digit **record count** rather than the dealer id (pcn874.py:26,115) |

**What this validator does:** requires `X` + the same dealer id as the header, and the finding text
names the `linet3` `Z` reading explicitly so nobody thinks it was overlooked. Two sources plus two
artefacts; a wrong trailer letter is a rejected filing, so this is deliberately an error rather than
a warning.

### 5.6 Line endings, trailing newline, and whether a detail-free file is legal

- Line endings: `accounter` writes LF (builders.ts:37,41); `rcbuilder` writes the platform newline
  via `AppendLine` (PCN874Manager.cs:571-575), which is CRLF on Windows; the excluded `cfo` writes
  CRLF explicitly. **This validator accepts LF, CRLF and CR**, and reports *mixed* endings as a
  warning.
- Trailing newline after the footer: absent in `accounter`, present in `rcbuilder`. **Accepted
  either way.**
- Zero detail records: `accounter`'s validator rejects a file with fewer than 3 lines
  (index.ts:31-34), so a period with no transactions would be "invalid" to it. `rcbuilder` has no
  such rule and its repo contains `PCN874_Sample_No_L_AND_NO_S_transactions.txt`. **This validator
  reports an empty period as a warning, not an error** — a genuinely quiet month is not a
  malformed file.

### 5.7 The `reportedVat` arithmetic — three different formulas, so no rule was written

| source | formula for the last header field |
|---|---|
| `accounter` | none — the caller supplies `totalVat`; the README lists "header vs transactions sum validation" as an open TODO (README.md:9-10) |
| `rcbuilder` | `taxableSalesVat − otherInputsVat` (PCN874Manager.cs:455) — equipment inputs excluded |
| `linet3` | `t_vat + ns_t_vat` (FormReportPcn874.php:150) — **inputs excluded entirely** |

Three sources, three answers, and one of them says it does not know. **This validator implements no
`reportedVat` cross-check at all.** Adding one would mean choosing a formula on no evidence, and the
harm from a wrong VAT position is the filer's, not ours.

### 5.8 Sign of exactly zero

`accounter` writes `+` for zero (`value >= 0 ? '+' : '-'`, data-handlers.ts:28). `rcbuilder` writes
`-` for zero in the `reportedVat` field (`diffTotalVATtoToPayReceive <= 0`, PCN874Manager.cs:455-462).
**This validator accepts both `+` and `-` on every signed field** and asserts nothing about zero.
