# The channel loop — the board's design (Fable, 27.9.2026)

The owner's order of 27.9.2026 (verbatim in `MISSION.md`) asked for channels without limit, opened without stopping. This is the board's design for that loop. It was written by one Fable agent from a verified status report (4 Opus readers plus 1 Fable refuter) and three Opus scouts (`scouts.json`). The operational state it defines lives in `logs/CHANNEL_LOOP.md`. This file is the reasoning behind it and is not rewritten.

> Main-thread deviation (recorded, not hidden): the loop fires into the **same** session rather than a fresh one per tick (`create_new_session_on_fire`), because a fresh session gets its own branch and PR and loses PR #3's ownership. Between 6-hourly firings, a tick that still has owner-free work re-arms itself in about 60 minutes. That is how "non-stop" is honoured without ticking faster when the caps bind.

## How the order is read

The directive adds a standing goal (channel count, unbounded) and a sequencing rule (when a channel is ready and running, build the next; never idle by choice). It is read exactly as MISSION.md:312-331 already records it: 'unlimited' is a number of channels, not a loosening of anything above it. Concretely, what changes: (1) channel opening becomes a scheduled loop with its own state file (logs/CHANNEL_LOOP.md), not a sweep the owner has to ask for; (2) admission is continuous — one candidate per Fable sitting — instead of 121- or 18-candidate sweeps; (3) the loop maintains ONE batched owner-ask list and never invents a step per channel; (4) the loop caps built-but-unlaunched inventory, because today ~6 products are built and none is public (status.json done.liveInPublicNow = []; products/README.md:5-13) — a loop that only builds would pile inventory. What does NOT change: (a) honest value outranks the count (MISSION.md:362-367): a channel that can only exist by misleading a buyer, selling what is free, or violating terms is killed, not counted; (b) constraints 6-8 remain the admission gate — a 'channel' must have something of its own to sell (constraint 6, MISSION.md:155-170, checkHonestStorePlan in growth.ts:301), a named acquisition channel tested with the cheapest stranger-find test BEFORE the product (constraint 7, MISSION.md:188-192), and a named non-public input or an explicit ₪0-instrument status in code (constraint 8, MISSION.md:216-231); variants of an existing store are not channels (constraints.ts:44-64 screenProposal); (c) accounts do not multiply (constraint 2, MISSION.md:126-131): the loop prefers channels that ride accounts already on the seven steps (Gumroad, Apify, Netlify, GitHub org, domain); a channel needing a NEW account is a 'proposed step 8+', recorded in the batch, tested at ₪0, and never built or opened by the agent until the owner says yes — owner-steps.test.ts fails on an eighth step by design (owner-steps.ts:18-19); (d) money is still only a revenue_ledger row with a platform transaction id (MISSION.md:350-353): a channel 'running' at ₪0 is reported as ₪0, prominently (MISSION.md:50-52), and the count of running channels is reported beside it — never the count of built products or candidates; (e) the ₪200 one-off float is unchanged and already earmarked for the domain's first year (owner-steps.ts:138); no recurring charge for any channel (MISSION.md:264-266) — Netlify free, Apify free, Gumroad free, GitHub free; (f) nothing public carries the owner's name, username, Gmail, or the personal repo URL until step 7 (MISSION.md:296-300; the repo is PUBLIC with the owner's real name in merge-commit metadata — status verdict, correction A); (g) the owner does nothing recurring: a channel needing per-item owner action (per-win forms, per-deal signatures, per-report signed-in web forms, per-upload clicks) is not a channel, the same ruling that deferred Devpost (portfolio.ts:383-385; docs/REJECTED.md:1283). One consent is asked for explicitly rather than inferred: the repo's convention that the agent does not merge to main on its own initiative (owner-steps.ts:96; docs/OWNER_STEPS.he.md:43-44) is incompatible with 'non-stop' unless the owner grants a standing consent once; guessing the more generous reading with someone else's repo is not ours to do (MISSION.md:253-254 by analogy), so it is owner ask #1.

## "Ready and running" — when the loop moves on

A channel is READY AND RUNNING when all six hold, each checkable from origin/main or a runner, none from the container's memory: (1) PUBLIC — a stranger-reachable URL or listing exists under the brand, returned HTTP 200 by a GitHub runner probe (render-watch.yml or a probe job; the container cannot reach Netlify/Apify/Gumroad — status.json conn.networkLimits), and the built public artefact has ZERO hits for the owner identifiers (legal name, Gmail, GitHub username, Netlify team slug) — the 7.9 _site check (logs/CHECKPOINT.md:406-407) made a standing gate. (2) INSTRUMENTED — the channel's named stranger-reach KPI (strangerUsers30d, weekly cookieless page views, claimableBounties, npm downloads, plays) is written into colony.db by a scheduled job on main through recordKpi (ledger.ts:680; measurements.ts:77-102 pattern), and at least TWO consecutive scheduled writes have landed with real readings (a job that exists but has never written is not an instrument — the apify-publish.yml no-op runs are the precedent). (3) MONEY PATH DECLARED — either its rail's ledger connector is wired in colony.yml (today only Gumroad/Lemon Squeezy/Stripe, colony.yml:61-63) so a sale books with a transaction id, or the channel is coded as a ₪0 instrument/experiment (portfolio.ts:73 'instrument only'; status measuring, experiments.ts) — never a third state where money could arrive uncounted (rails.ts:76 observable:false for Apify is acceptable only while the line is an instrument). (4) GOVERNED IN CODE — its seed has killCriteria, scaleCriteria and a TARGET_BASIS entry with rail and acquisitionChannel (target-basis.test.ts refuses blanks, portfolio.ts:249-255), and decideLine (rules.ts:30) or evaluateExperiment (experiments.ts:235) reads its KPIs on every tick. (5) SMOOTH — two consecutive colony ticks on main (≈8-9 h at the measured 4.3 h cadence) report no blocker and no 'invalid' measurement for that channel (REPORT.md blockers section; runner.ts result.blockers), and the tick's own liveness check has not fired (runner.ts:137 LOOP_GAP_ALERT_MS). (6) RECORDED AND VERIFIED — a row in CHANNEL_LOOP.md's channel table moves from 'running-claimed' (written by the Opus tick) to 'running' only after a Fable verification agent has re-derived (1)-(5) from the cited evidence — because a confident claim nobody checked is this repo's named recurring defect (CLAUDE.md, verification-before-completion). 'Running' is deliberately NOT 'live': live means money landed (MISSION.md:352-353). The loop moves on at 'running'; the ledger, not the loop, promotes to live.

## The move-on rule and the caps

The loop advances the highest-ranked channel it CAN advance without an owner action, and starts the next channel on any of four triggers: (T1) the current channel is verified 'running'; (T2) it is PARKED-OWNER — its next step is an owner action — AND its 'minute-after checklist' is complete (everything that must happen the minute the owner acts is built, tested and written down, e.g., the deploy command, the Publish message, the sync-portfolio + report sequence), so the owner's action converts straight into a public surface; (T3) it is PARKED-WINDOW — its next step is a dated read (Algora week 4, Apify day 30, K0 day 56, 8-week page views) — with the read date and the file it reads written in the measurement calendar; (T4) it is killed, with the REJECTED.md entry and reopen trigger written and sync-portfolio applied. Parked channels do not hold the loop (MISSION.md:324-327); every tick re-checks their unpark conditions first. INVENTORY CAP: built-but-unlaunched (BBU) channels — code built past a first-stranger test, no public surface, next step owner-dependent — may never exceed SIX, which is today's count (apify-il-open-data, il-biz-tools, pcn874, mcp-il-tools, the T1 web page, the T1 video; products/README.md:7-13), so the cap binds immediately and by design: no new build whose launch depends on an owner step starts while BBU ≥ 6. ACCOUNT CAP: a candidate whose launch needs a NEW owner account or step beyond the seven may be TESTED at ₪0 and queued, but never built until the owner has said yes to that step in the batched list (owner-steps.ts:18-19: an eighth step needs a decision, not a commit); the kids channel is a click-set inside Stage A on T1's account, not a new account (ruling 4.10 §7, research/channel-loop/RULING-2026-10-04-kids-youtube.md). CONCURRENCY CAPS: ≤1 product build in flight, ≤3 experiments in 'measuring' (types.ts:247 maxExperiments, value 3 at :259), ≤1 render-watch dispatch per tick (the 7.9 race, render-watch.yml:50-52). WHEN THE CAPS BIND (as they do today), the loop's work shifts, in this order, to: (i) minute-after prep that makes parked inventory launch-ready without adding to it (the three il-biz-tools pre-deploy defects, the PostHog key, the pcn874 validator page riding the same deploy, mcp-il-tools' two defects and publish workflow); (ii) ₪0 stranger-find and payability tests for queued candidates, batched into one render-watch dispatch per tick plus GitHub-hosted reads; (iii) instruments and measurement plumbing (the mlcontests count, connectors for rails a line has chosen); (iv) admission research and the daily Fable ruling; (v) maintaining the single owner-ask batch; (vi) maintenance (doc drift such as 'runs hourly', stale claims, tests) — and when nothing remains the tick records 'idle-by-cap' honestly rather than building to look busy. The loop never advances a measured clock, never restarts one to look fresh, and never counts a parked or BBU channel as opened; the owner's report shows running channels beside ledger shekels.

## Cadence and the model split

The loop fires as a scheduled Claude session every 6 hours (a Routine with create_new_session_on_fire so each tick starts from written state, MISSION.md rule 6; cron on a jittered minute such as `11 1,7,13,19 * * *` UTC), each tick bounded to roughly 45 minutes of agent time and a token budget, with anything longer dispatched as a repo-resident workflow script. Why 6 h: GitHub's 'hourly' colony cron actually lands about every 4.3 h with gaps to 6.5 h (status verdict correction B: 28 runs in ~120 h), so a 6-hourly loop sees at least one fresh tick almost every time; the colony's own supervisor review is 6-hourly and the board daily (docs/OWNER_STEPS.he.md:69-70); every measurement in the plan moves in days to weeks (Apify daily 05:41 UTC, Algora Mondays 06:23 UTC, render-watch Tuesdays 05:23 UTC, K0 at day 56), so ticking faster would only re-read the same files; and with the inventory cap binding there is nothing a faster build cadence could buy. The same schedule the owner already had (`24 */6 * * *`, disabled on 8.9 after 'stop') is re-enabled under the 27.9 order; the ad-hoc hourly PR #3 re-check routine folds into it. Model split: OPUS does everything routine — probes, prep, builds, connectors, ₪0 render dispatches and reading them, scouts (≤7 per tick), doc and state edits, tests. FABLE is used at exactly four gates and nowhere else: (a) admission of a candidate whose ₪0 test has returned; (b) kill / scale / retarget rulings when a dated read arrives or decideLine derives a kill; (c) verification that a 'running-claimed' channel is really public+instrumented+governed before the loop moves on; (d) any proposed owner step. One Fable sitting per day (the ~07:11 UTC tick), ≤2 Fable agents, always after the one-word probe; a 429 queues the item in logs/FABLE_QUEUE.md and the Opus work continues — the quota died twice (~40 h on 25-27.9, CHECKPOINT.md:86,128-137) and both deaths were Fable fan-outs, so Fable is never in a fan-out and never waits in a loop. Every agent sets model explicitly (CLAUDE.md fleet rule).

## What the state file holds

logs/CHANNEL_LOOP.md is rewritten every tick from probes (never appended forever; per-tick history lives in logs/YYYY-MM-DD-channel-loop-tick.md) and holds, in this order: (1) HEADER — last tick UTC, branch and commit, routine id, Fable probe result, which tiers ran, a two-sentence Hebrew summary for the owner stating running channels = N and ledger = ₪X (today 0 and ₪0.00). (2) PROTOCOL — the tick protocol, the 'ready and running' definition, the move-on rule and the caps (this design), so a fresh session needs no other file. (3) CAPS AND COUNTS — BBU n/6 with the named members; experiments measuring n/3; builds in flight n/1; the Fable items queued. (4) CHANNEL TABLE — one row per channel: id; stage (candidate → testing → admitted → building → launch-ready → parked-owner | parked-window → running-claimed → running → live | killed); rail and whether a ledger connector exists; acquisition channel; non-public input or 'instrument ₪0'; owner steps needed (existing # / proposed step 8+); next action; unpark condition and expected date; evidence (path:line, run id, commit, runner probe); last verified UTC. (5) RANKED QUEUE of candidates with each one's ₪0 test, its status (not run / dispatched run # / returned: verdict) and the research/measurements/ file it writes. (6) PARKED LIST sorted by expected unpark date, each with its minute-after checklist and a checkbox per item. (7) MEASUREMENT CALENDAR — dated reads (Algora weeks 1-4 from the first Monday after merge; Apify day 30 from the Publish click; il-biz-tools 8-week page views and 90-day revenue from the DOMAIN deploy; T1 web arm day 56 from its deploy; K3 day 112) with the file each reads. (8) OWNER-ASK BATCH — the single ordered list below, minutes per item, what each unblocks, proposed steps marked 'needs your yes', and the 'held, not asked' list (step 4 until week 4; Stage A until day 56; Apify KYC until 50 users). (9) KILLS AND ADMISSIONS made by the loop with the REJECTED.md / portfolio.ts lines. (10) OPEN FABLE ITEMS — pointer into logs/FABLE_QUEUE.md. (11) NEXT TICK'S FIRST ACTION — one concrete line. (12) RESUME — how to run one tick by hand (`Workflow({scriptPath: 'scripts/workflows/channel-loop-tick.js'})` once written), the routine id, and the stale-worktree check. Ownership: the tick's main thread writes it; worktree agents never do (CLAUDE.md agent-worktrees). It duplicates nothing that the ledger owns — money figures are quoted from origin/main REPORT.md with the tick commit, never typed.

## The tick protocol

1. GROUND. Read MISSION.md, then logs/CHECKPOINT.md, then logs/CHANNEL_LOOP.md. Run `git log --oneline -1`, `git status`, `ls products/ src/revenue/`; if the checkout is stale, `git reset --hard origin/<branch>` (CLAUDE.md worktree lesson). If CHECKPOINT records an owner 'stop' since the last tick, write state and exit.
2. PROBE TRUTH ON ORIGIN/MAIN, NOT THE BRANCH. Record with UTC time: latest 'colony tick' commit and REPORT.md blockers; kv last-run rows; KPI rows for running channels; presence and age of state/colony/measurements/*.json; PR #3 state and head via the API; render-watch outputs since the last tick; the one-word Fable probe (OK/429). Every probe result is written into CHANNEL_LOOP.md before any work — a fact carried forward unverified is the repo's named defect (status verdict corrections B-D: 'hourly' was never measured).
3. UNPARK. For each parked channel compare its unpark condition (an owner word recorded in CHECKPOINT, a file that appeared, a date reached) with the probes; re-activate matches and put their minute-after checklist at the top of this tick's work.
4. REVIEWS DUE. Read decideLine / evaluateExperiment outputs for every running or measuring channel from the tick results; any code-derived kill, scale, retarget, or a dated read that is due becomes a Fable item in logs/FABLE_QUEUE.md. A code-derived kill is applied after Fable confirms it, or after two skipped daily Fable sittings (48 h) — then the code's verdict stands (auditDecision, rules.ts:231-243, accepts stricter never softer).
5. RECOUNT CAPS. BBU vs 6; experiments measuring vs 3; builds in flight vs 1; render dispatches this tick vs 1. Write the numbers.
6. PICK WORK, in order: (a) minute-after prep for parked channels not yet launch-ready; (b) ₪0 tests for queued candidates, batched into ONE render-watch dispatch from the branch plus GitHub-hosted reads; (c) instruments and measurement plumbing; (d) the top-ranked admitted channel's build only if every cap allows and its launch needs no unapproved owner step; (e) otherwise maintenance, and record 'idle-by-cap'.
7. EXECUTE ON OPUS. Every subagent sets model:'opus' explicitly (CLAUDE.md fleet rule); builders work in worktrees and every brief opens with the base check; ≤7 scouts, ≤1 product build, ≤1 render dispatch per tick; anything longer than a tick is a script in scripts/workflows/ so a fresh container resumes from the repo (scripts/workflows/README.md). Worktree agents never edit CHECKPOINT.md or CHANNEL_LOOP.md.
8. VERIFY BEFORE CLAIMING. `pnpm typecheck`, targeted vitest, product tests; any 'public' claim only from a runner probe (200) plus an owner-identifier grep of the built artefact; 'the job runs' only from a run id and a written file; never claim 'live' or 'running' from the container.
9. FABLE SITTING — once a day (the ~07:11 UTC tick, after the 05:41 Apify count and Monday's 06:23 Algora count have landed), ≤2 Fable agents, only if the probe passed: admission ruling on the top candidate whose ₪0 test returned (ADMIT / KILL / TEST_MORE against the gates); the kill/scale rulings queued in step 4; verification of any 'running-claimed' channel before it becomes 'running'; a ruling on any proposed owner step. Rulings go to research/…, docs/REJECTED.md (kills, with reopen triggers) or src/revenue/portfolio.ts (admissions, with TARGET_BASIS), then `sync-portfolio` + `report` once on main. If 429: queue in FABLE_QUEUE.md, continue the Opus work, never decide a kill or admission on Opus.
10. OWNER-ASK BATCH. Rebuild the single ordered list from the channel table — only steps a channel is actually blocked on, nothing invented (MISSION.md:344); proposed steps 8+ flagged as needing the owner's yes; if it changed, the report's per-line open-steps text follows (the branch's generator already lists them).
11. WRITE STATE. logs/CHANNEL_LOOP.md rewritten in full from the probes; logs/CHECKPOINT.md pointer (branch, where stopped, next step); logs/YYYY-MM-DD-channel-loop-tick.md in Hebrew per CLAUDE.md; commit and push to the branch. Main moves only by merge under the owner's standing consent (ask #1) or by the colony bot.
12. RE-ARM. The routine fires again in 6 h. If a sooner wake is expected (a merge, an owner word), schedule one send_later; nothing waits on Fable — queued items carry over. Tick 0 (now, 27.9): write CHANNEL_LOOP.md with this design and queue; fix the three il-biz-tools pre-deploy defects and create the PostHog project key; dispatch one render-watch with the ₪0-test URLs (stripe.com/global, Stripe cross-border, Wix payments FAQ, docs.crazygames.com faq/payouts/terms, portal.astro.build paid themes API, api.topcoder.com active challenges); write the owner-ask batch; replace the hourly PR #3 re-check routine with the 6-hourly loop routine (create_new_session_on_fire); checkpoint, Hebrew log, commit, push.

## Stop conditions

- A channel's next step is a NEW owner account or step beyond the eight: that channel pauses at 'tested' and joins the owner batch as a proposed step; the loop continues on other channels. The agent never opens the account or answers an identity check (MISSION.md:345-347).
- Any spend beyond the remaining ₪200 one-off float, or any recurring charge (a subscription, a paid tier, private-repo Actions minutes beyond the free allowance if they cost money): stop that item and ask; the float never becomes rent (MISSION.md:264-266).
- Money could arrive before the tax file: if the owner completes step 3 (Gumroad) before confirming step 2, paid activation (Pro product creation, any price on pcn874 or a theme) is held and the owner is told why (docs/OWNER_STEPS.he.md:95).
- The first surface under the brand name: the owner is told in one line that the name goes public with the next deploy and may veto (brand-name-decision.md:3-6); netlify.app surfaces proceed after one tick, irreversible commitments (domain, org, store) are their own clicks.
- Any public artefact would link to or expose the personal repo URL or the owner's name in commit history: hold that link until the owner decides ask #8 (private repo vs accept) — nothing else in the channel waits.
- The only way to raise the channel count is a variant, an account farm, or a per-item owner action: stop that branch, say so in CHANNEL_LOOP.md and the report, do not do it (MISSION.md:133-138, 155-170, 329-331).
- A platform enforcement signal against the brand on any platform: pause every launch on that platform, kill the affected channel the same day, inform the owner in the report (brand contagion, RED-TEAM §2.2).
- The colony tick on main has not run for over 24 h (LOOP_GAP_ALERT_MS is 6 h, runner.ts:137): no new public surface goes up blind; fix the loop first, tell the owner if a GitHub setting is the cause.
- Fable is out (429) and a kill, scale, admission or owner-step ruling is due: do not decide on Opus; queue it in FABLE_QUEUE.md, continue the Opus work, and after 48 h let a code-derived kill stand. Not an owner ask — recorded as a decision lag in CHECKPOINT.md.
- The owner says stop (as on 7.9 and 8.9, CHECKPOINT.md:244-264): the tick writes state, disables the routine, and ends; nothing resumes until they say so.
