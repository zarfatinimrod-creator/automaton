## Part 2 — findings in detail

### F1 — WRONG, HIGH — line 117: the spec watch cannot notice a new edition

> "`.github/workflows/pcn874-spec-watch.yml` watches all three hashes so a new edition is noticed rather than assumed away."

**Evidence.**

- `products/pcn874/docs/SPEC-SOURCES.lock.json` — `"sources": {}`. No hash has ever been stored. Same
  on `origin/main` (`git show origin/main:products/pcn874/docs/SPEC-SOURCES.lock.json`).
- `tests/spec-watch.test.ts:38-41` **pins it empty**: `expect(lock.sources).toEqual({});` with the
  comment "the hashes in research/rendered/*.meta.json came from the render-watch workflow, not from
  this job".
- `scripts/spec-watch.mjs:123-125`: when a source has no previous entry it prints `new` and exits 0.
  Only a stored `previous.sha256` that differs sets `changed = true` (`:126-130`) and exits 1 (`:160-167`).
- `.github/workflows/pcn874-spec-watch.yml:30-31` `permissions: contents: read`, and the job has no
  commit or push step. It uploads only `.spec-downloads/` as an artifact, not the lock. So every run
  starts with the empty lock from git, sees three `new` sources, and exits 0. The `CHANGED` branch
  cannot run in CI as wired. A green run means nothing about whether the document changed.
- The weekly `render-watch.yml` does re-fetch the three URLs (`research/rendered/urls.txt:93-95`) and
  would commit a changed PDF plus `meta.json` with `"changed": true`. But it exits 0 on change
  (`scripts/render-watch.mjs:35`, "exits non-zero only when the script itself is broken"), commits with
  `[skip ci]` (`render-watch.yml:128`), and does not regenerate the `.txt` that the validator's tests
  read (`meta.json` `"textPath": null`). A new edition would arrive as a silent commit that nobody is
  alerted to and no test sees.

**Why HIGH.** `docs/SPEC.md` §5.6 calls "whether the layout has changed since 2009" "the largest open
question". This sentence tells the owner a safeguard exists, and it does not. For a product that
writes tax filings, a silently superseded layout is the most expensive failure there is.

**Proposed fix (wording only):** "No automated check fails on a new edition today.
`pcn874-spec-watch.yml` downloads the three documents, but its lock file
(`docs/SPEC-SOURCES.lock.json`) has never held a hash and the job cannot commit one, so it cannot
detect a change. The weekly `render-watch.yml` re-fetches the same three URLs and would commit a
changed PDF under `research/rendered/`, but it does not fail or alert and it does not refresh the
extracted text. Noticing a new edition currently depends on someone reading that commit." (Or: fix the
workflow so the claim becomes true, and only then keep the original sentence.)
