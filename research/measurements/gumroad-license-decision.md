# il-biz-tools Pro — how the licence is issued: **Option C** (Gumroad's own key, verified once from the browser, then cached; re-checked at most every 7 days; never revoked on a transient failure)

## 1. Decision

**Option C.** Pro is unlocked by the licence key Gumroad mints for every sale and prints in the buyer's receipt (Q1, CODE). The page verifies it once, from the buyer's browser, at `POST https://api.gumroad.com/v2/licenses/verify` with only `product_id` + `license_key` (Q2, CODE; Q3 RENDERED 25.9: `access-control-allow-origin: *` on both preflight and POST through Cloudflare). It stores the key, the product id and the check time in `localStorage`, discards everything else Gumroad returns, and Pro then works offline. In the background it re-checks at most once every 7 days with `increment_uses_count=false`, and it switches Pro off **only** on a definitive answer — a 404 from Gumroad (key disabled, key not found, access revoked) or a 200 whose flags say refunded / chargebacked / disputed-and-not-won. A network error, a timeout, a 429, a 5xx, a non-JSON body or any unexpected shape keeps the cached Pro exactly as it was.

The owner does nothing per sale. Nothing is added to his seven steps. The signing keypair, `scripts/make-license.js` and the `ILBIZ1.` format are retired: no keys were ever issued, so nothing breaks.

## 2. Why C — against the weights the task set

**A recurring owner step is disqualifying.** C has none. Gumroad mints the key on the `successful` transition (`purchase.rb:248`, `:2144-2145`, `:2171`) and prints it in the receipt (`receipt/_item.html.erb:27-30`). The one precondition — a licence-key block in the product content — is per product, once, and the scope table above makes it agent work through the token the owner already mints at step 3 and pastes at step 6. If the live API call fails, the fallback is one dashboard click ("Insert → License key", `_76`), which would be a one-time click and is flagged in §7 rather than pre-emptively added to the checklist.

**Honest value to the buyer.** What is sent, when: the key and the public product id, to Gumroad only, once at activation and at most every 7 days after, from the buyer's own browser. Gumroad already holds this buyer's email, card and IP as merchant of record; the check gives it nothing it does not have except "this person opened the invoice page today". Nothing is sent to us — there is no us. Pro works offline after the first activation. The buyer pays once, may use the key in any browser, and is never locked out by our downtime, because there is none, or by Gumroad's, because the cached state is honoured until Gumroad says otherwise.

**Refunds and chargebacks.** Gumroad does not fail `verify` on a refund; it returns 200 with `refunded: true` / `chargebacked: true` / `disputed` (Q4a, CODE; Gumroad's spec asserts it). C reads the flags on every check, so a refund switches Pro off at the next re-check — within 7 days of use, not instantly. That lag is accepted: the alternative (check on every use, option B) costs the buyer offline use and a request per print. A dispute the seller **wins** (`disputed: true, dispute_won: true`) must keep Pro on — the classifier rule is explicit about it. The colony's hourly sync already writes refunds to the ledger from the sales API (`src/revenue/connectors/gumroad.ts`, `sale.refunded`); disabling refunded keys by API from that sync is possible with `edit_products` and is left as an optional follow-up, not a requirement — the flags already suffice and a wrong disable would take Pro from a paying buyer.

**Network error or 429.** The rule is asymmetric on purpose: **only a definitive answer changes state.** Definitive = HTTP 404 with a JSON body whose `success` is `false`, or HTTP 200 with `success: true` and a revoking flag. Everything else — no network, timeout, 429, 5xx, 400, a Cloudflare challenge page, a body that is not JSON, a 200 without `success: true` — is "unknown" and leaves the cached record untouched, including its `lastCheckAt`, so the next page load retries. A paying buyer cannot lose Pro to anything transient. Rate limits are unknown in number (Q4b) and the load is designed to be irrelevant to them: one request per activation and at most one per browser per week; a hundred active buyers would mean about fifteen requests a day.

**First activation is the one moment C needs the network**, and there it cannot be made better without a server: if Gumroad is unreachable, the key is kept as `pending`, the buyer is told plainly that nothing is lost and the page will retry on its own, and the page never says "invalid" for a transient failure. Options D and B need the network at the same moment; only A and E avoid it, and both are rejected below on grounds that outweigh it.

**What the site promises today, sentence by sentence.** The site stays static — no server of ours, no build-time transformation, `_site/` is still a copy. "Static" remains true everywhere it is said. What does **not** survive unqualified is the family of "nothing is sent anywhere" sentences, because a licence key is data the buyer types and it is sent to Gumroad. The exact inventory and the replacement wording are in §5; the build must change every one of them, and AT-13 checks it.

**What is CODE-grade rather than measured, stated so nobody inherits it as fact.** Measured: CORS on preflight and POST through Cloudflare, and the exact 404 body for a non-existent key (25.9 runner). CODE only: that a real key returns the documented 200 payload with those flags (Gumroad's spec asserts it, we have not seen it); that a dashboard token carries `edit_products`; that `POST /v2/products` with a `licenseKey` node creates a licensed product (Gumroad's own FAQ says the API cannot create products — one of them is stale, and the build must find out from a runner, AT-15). Unknown: rate limits; how Gumroad's review after the first 3-4 sales reads a web-feature licence. And the one thing that cannot be rendered without a purchase: a real key verifying from a real browser. The first sale is that test. The build must therefore leave Pro labelled "on sale, first key not yet verified" (AT-17), and the ledger entry for the first `gumroad:<productId>` sale is the event that changes the label.

## 3. Rejected

| Option | Why not |
|---|---|
| **A** — our ECDSA key, owner issues per sale | A recurring owner action per sale (`make-license.js issue`), which `MISSION.md` §1 forbids, and a delivery channel that does not exist: the key is minted after the sale (`make-license.js:59`) but product content is fixed before the sale and identical for every buyer (owner-docs audit F4). Disqualified on the first weight alone. |
| **B** — Gumroad key verified on every use | No offline use; every print sends the key, IP and timing to Gumroad and brings the buyer's own email, name and card display back into the page; each use increments `uses` unless the flag is sent; exposure to unknown rate limits scales with usage rather than with sales. Everything B does, C does once. |
| **D** — Netlify Function exchanges a Gumroad key for our signed key | Adds a server and a secret to a site whose README truthfully says it has neither (`netlify.toml`, "no server-side env vars"), against MISSION constraint 1 (static over servers). It moves the buyer's key and IP from Gumroad, which already has them, into **our** function's hands and logs — a privacy step backwards for a site that collects nothing. Setting the env var is agent work only if a Netlify token with that permission exists (none is on the checklist: step 6 links Netlify by UI, deliberately without a token), otherwise it is a new owner step. It stays the documented fallback if Gumroad's edge ever stops honouring CORS — it is not adopted while the measurement says it does. |
| **E** — one static signed key shared by all buyers | A shared password. One leak unlocks Pro for everyone, no per-buyer revocation, no refund detection, and it is honest only if sold as exactly that — which is not a licence. Dominated by C. |
| Variant — the colony signs per sale in CI and delivers | No channel was found by which the agent hands a per-sale key to the buyer; up to an hour of delay; Gumroad's own key already solves delivery (Q1). |
| **NONE** | Not warranted: the measurement asked for one live fact before any option could be called workable — CORS from a foreign origin — and it was rendered on 25.9. The remaining unknowns are build-time (AT-15/16) or first-sale (AT-17), and each has a safe failure mode. |

## 4. The design the Opus build implements

The names below are what the acceptance tests refer to; the builder may rename, but each behaviour must exist and be tested as stated.

**Config (`src/config/site.json`).** `gumroad.productUrl` (unchanged, `""` by default) and **`gumroad.productId`** (Gumroad's public external id, `""` by default). The `pro` block and `pro.publicKey` are removed. Both fields are written by the product-creation job (below), not by the owner.

**Verifier (`src/lib/license.js`, rewritten).**
- `VERIFY_URL = 'https://api.gumroad.com/v2/licenses/verify'` — the `api.` host, never `gumroad.com/api` (the CORS rule keys on Host, Q3).
- `normalizeKey(input)` → trim + uppercase; `isGumroadKeyShaped(key)` → `/^[0-9A-F]{8}-[0-9A-F]{8}-[0-9A-F]{8}-[0-9A-F]{8}$/` (Gumroad: `SecureRandom.uuid.upcase.delete("-").scan(/.{8}/).join("-")`, `license.rb:38`). A key that is not shaped is never sent anywhere.
- `verifyWithGumroad({ productId, key, increment, fetchImpl, timeoutMs = 8000 })` → one POST, `application/x-www-form-urlencoded` body (`URLSearchParams`) so it is a CORS simple request with no preflight, `credentials: 'omit'` (so the anonymous session cookies Gumroad sets are ignored by the browser), `AbortSignal.timeout(timeoutMs)`, body `product_id=…&license_key=…` plus `increment_uses_count=false` when `increment` is false and nothing when true. Returns only `{ verdict, reason, uses }` — never the response body.
- `classifyVerifyResponse({ status, body })` — pure, the heart of the tests:
  - `200` + `body.success === true`: **revoked** if `purchase.refunded === true`, or `purchase.chargebacked === true`, or (`purchase.disputed === true` and `purchase.dispute_won !== true`), or any of `subscription_ended_at` / `subscription_cancelled_at` / `subscription_failed_at` is non-null; otherwise **active**.
  - `404` + parseable JSON with `success === false`: **revoked**, reason `disabled` / `not_found` / `access_revoked` by message (the three bodies at `licenses_controller.rb:38,86,89`).
  - Anything else — `429`, `5xx`, `400`, `404` with a non-JSON body, `200` without `success === true`, fetch rejection, `AbortError` — **unknown**.
- Storage under the existing `ilbiz.license` key, now JSON: `{ v: 1, key, productId, status: 'active' | 'pending', activatedAt, lastCheckAt, lastAttemptAt }` and nothing else. A legacy `ILBIZ1.` string is cleared and treated as no licence.
- `RECHECK_INTERVAL_MS = 7 * 86_400_000`; `shouldRecheck(record, now)` → `status === 'active'` and `now - lastCheckAt >= RECHECK_INTERVAL_MS`.

**Page glue (`assets/page-invoice.js`).**
- On load: read the record. `active` → Pro on immediately, no network. Then, if `shouldRecheck` and `navigator.onLine !== false`, one background verify with `increment: false` **using the record's own `productId`** (so a later config change cannot orphan existing buyers); `active` → `lastCheckAt = now`; `unknown` → `lastAttemptAt = now` only; `revoked` → Pro off, record removed, note names the reason. `pending` → one activation attempt (with increment) exactly as if the buyer had pressed the button.
- On "הפעלה": normalize; not shaped → note "המפתח אינו בפורמט הנכון" and no fetch; config `productId` empty → note "המיתוג עדיין לא הופעל באתר הזה" and no fetch; otherwise verify with `increment: true`. `active` → store, Pro on, "הרישיון אומת. המיתוג פעיל."; `revoked` → nothing stored, reason shown; `unknown` → store as `pending`, Pro off, note: the key is kept in this browser, nothing is lost, the page will retry on its own, or press again in a minute.
- "הסרת הרישיון" clears the record; no network.
- The Pro block still contains neither `renderClients` nor `nextDocumentNumber` (existing honesty test).

**Button (`src/lib/gumroad.js`).** `proButtonState` requires `productUrl` **and** `productId`; the state `no_public_key` becomes `no_product_id` with the note "החנות מוגדרת אך עדיין אין מזהה מוצר לאימות הרישיון, ולכן אי אפשר למכור." The `ready` note becomes: "התשלום מתבצע ב-Gumroad. מפתח הרישיון מגיע בקבלה במייל מ-Gumroad; הזנתו כאן נבדקת מול Gumroad פעם אחת ומפעילה את המיתוג."

**CSP (`netlify.toml`).** `connect-src 'self' https://plausible.io https://*.posthog.com https://api.gumroad.com`. `script-src` and `frame-src 'none'` unchanged — no Gumroad code runs on the page.

**Retired.** `scripts/make-license.js`, the ECDSA path, `pro.publicKey`, every `ILBIZ1` string (the input placeholder becomes `XXXXXXXX-XXXXXXXX-XXXXXXXX-XXXXXXXX`).

**Product-creation job (`.github/workflows/gumroad-pro-product.yml`, `workflow_dispatch`, agent side, needs `GUMROAD_ACCESS_TOKEN`).** Idempotent: `GET /v2/products` and reuse the product by name if it exists; otherwise `POST /v2/products` **as a draft** (`create_as_draft?` — the builder reads the parameter name at the pinned commit) with the price the board set, a description that says exactly what Pro is (logo and accent colour on the printed document, on this site, one internet check at activation, one-time, no subscription), and `rich_content` holding written Hebrew activation instructions plus a `licenseKey` node (`RichContent::LICENSE_KEY_NODE_TYPE = "licenseKey"`, `rich_content.rb:14`); optionally a downloadable guide by URL (`files`), hosted on the site, never under the owner's GitHub username. Read back `GET /v2/products/:id`; assert the rich content contains the `licenseKey` node (or `is_licensed`, if the API JSON exposes it — the builder checks the shape). Print `id` and `short_url` (both public) and open a PR that writes them into `site.json`. Enable the product (`PUT /v2/products/:id/enable`) only in a second dispatch, after the deployed `site.json` carries the same id. The token is passed by env and never echoed. The job log is the RENDERED evidence for the API-creation question and is pasted into a follow-up section of this file.

## 6. The buyer-facing disclosure (exact text the Pro box must carry)

Visible beside the key input, always: **"מפתח הרישיון נבדק מול Gumroad פעם אחת בהפעלה, ואחר כך לכל היותר פעם בשבוע."**

Full text, inside `<details>` titled "מה נשלח לאן" in the Pro box:

> **מה נשלח לאן.** האתר הזה סטטי: אין לנו שרת, והקבלות, רשימת הלקוחות והלוגו שלכם נשמרים בדפדפן שלכם בלבד ולא נשלחים לשום מקום.
> חריג אחד, ורק ב-Pro: כשמזינים מפתח רישיון, הדפדפן שלכם שולח את המפתח ואת מזהה המוצר ישירות ל-Gumroad (`api.gumroad.com`), כדי לוודא שהמפתח שולם. Gumroad, כמו כל שרת שפונים אליו, רואה גם את כתובת ה-IP שלכם, סוג הדפדפן וכתובת האתר הזה. אחרי ההפעלה הבדיקה חוזרת ברקע לכל היותר פעם בשבוע.

## 9. Open risks

1. **Rate limits are unknown in number (Q4b).** Mitigated by design (one call per activation, ≤ one per browser per week). If Gumroad's edge answers a browser with a bot challenge (403 HTML without CORS headers), first activations fail as `unknown` and go `pending` until it clears — there is no fallback short of Option D.
2. **API product creation is CODE-grade and Gumroad's own FAQ contradicts it.** AT-15 settles it live. Failure mode: one dashboard click, raised to the owner before any sale.
3. **Gumroad's review after the first 3-4 sales** may read a web-feature licence differently from "software". Gumroad's help text supports the shape and the product carries real content; still not a ruling. The existing kill criterion "Gumroad account rejected or the seller review fails" covers it.
4. **The first real key verifies only with the first real sale.** The first buyer is the live test. Made safe: transient failures never read "invalid", the key is kept and retried, and the README says "not yet verified" until the ledger says otherwise.
5. **Refunds are a customer contact the owner does not do.** `refund_sales` is not in the minted scopes, so the colony cannot refund by API; a refund request lands in the seller's Gumroad inbox. This belongs to the whole Gumroad rail, not to this decision, and the seller's refund-policy setting and Gumroad's buyer-side handling need a read before the first sale.

   > **Correction, 28.9.2026** (`research/tiktok/08-sales-marketing-lessons.md` §4.5, N14e; read in antiwork/gumroad main on 28.9.2026, not run).
   > `app/controllers/api/v2/sales_controller.rb:7` authorises refund with `doorkeeper_authorize! :refund_sales, :edit_sales`,
   > `base_controller.rb:7-8` adds `:account`, `config/initializers/doorkeeper.rb` puts `edit_sales` and `account` in
   > `public_scopes`, and `app/models/oauth_application.rb:121-122` gives a new application `public_scopes` by default. So a
   > dashboard-minted token carries a scope the refund action accepts (by Doorkeeper's any-of scope semantics); the
   > colony can refund by API. The remaining gates are a mailbox the agent reads, a responder, and a Gumroad balance that
   > covers the refund. Item 5 is left as it was written.

6. **Buyer PII transits the buyer's own browser** in the verify response (email, name, card display, `ip_country`). A property of Gumroad's API we cannot switch off; discarded on arrival (AT-9) and disclosed (§6).
7. **Client-side gating is bypassable** by editing JavaScript — unchanged from today and already stated in the README.
8. **Key sharing is not enforced against.** No seat count; the seller sees `uses`. Accepted and disclosed ("any browser").
9. **Refund detection lags by up to 7 days** of the buyer's use. Accepted for offline use; optional follow-up: the hourly sync disables refunded keys via `PUT /v2/licenses/disable`.
10. **Clearing site data loses the activation.** One re-entry from the receipt; disclosed.
11. **Anonymous session cookies** set by `api.gumroad.com` on the response are ignored under `credentials: 'omit'` — CODE/spec behaviour of `fetch`, to be confirmed in a real browser when a key exists.
12. **Pricing currency.** Whether Gumroad lets this product be priced in ILS was not checked here; the board's ₪79 may become a USD price.

## 10. Decision path

Read `MISSION.md` (rule 1: one checklist, never a recurring owner task; rule 4: honesty outranks revenue; constraint 1: static over servers). Read the measurement: Q1–Q5 CODE, Q3 RENDERED on 25.9, Q4b UNKNOWN, options A–E. Eliminated A on the recurring step and the non-existent delivery channel (F4). Weighed B/C/D/E on the five weights the task set: B loses offline use and multiplies PII exposure per use; E is a shared password with no refund detection; D adds a server and a secret to a truthfully static site and moves buyer data into our hands — kept only as the fallback if CORS ever fails live. C keeps the buyer offline after one check, sends the key only to the party that already has the buyer's data, detects refunds by flag, and survives every transient failure by construction. Then closed the two unknowns that decide whether C costs the owner anything: fetched Gumroad's OAuth model, Doorkeeper config and dashboard controller at the pinned commit — the minted token carries `edit_products`, so the licence-key block is agent work; fetched the products API controller — creation with `rich_content` exists in code while Gumroad's FAQ denies it, so it is CODE, not RENDERED, and AT-15 exists to settle it. Spent one of two WebSearch calls on rate limits; only third-party "unpublished, 429s happen" came back, so Q4b stays UNKNOWN and the design tolerates it. Inventoried every "nothing leaves the browser" sentence on the site and in the docs and wrote the replacements.
